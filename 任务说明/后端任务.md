后端流程逻辑
1. encounter 创建

当前端请求创建 encounter 时，后端需要：

生成唯一 encounter id

初始化 patient memory

初始化当前房间为 lobby

初始化阶段为 triage

初始化状态为 in_progress

初始化一条系统消息，例如：

“Please go to the triage room.”

2. move 行为

当前端通知患者进入某个房间时，后端需要：

更新 current_room

判断当前阶段与该房间是否匹配

返回是否可进行下一步交互

例如：

在 triage 阶段进入 triage_room，可开始护士对话

在 consultation 阶段进入 doctor_room，可开始医生对话

在 pharmacy 阶段进入 pharmacy，可展示处方说明

3. message 行为

当前端发送一条消息时，后端需要：

保存用户消息

根据当前 stage 返回固定脚本响应

必要时推进流程阶段

返回新增消息和最新状态

例如：

triage 阶段

患者说第一句话 → 护士追问

患者说第二句话 → 分配内科并切换到 consultation

consultation 阶段

患者回答医生问题 → 医生提示将开检查

pharmacy 阶段

可以返回药师说明或结束消息

4. order-test 行为

当前端触发检查时，后端需要：

生成固定 mock 检查结果

保存到 clinical state

生成系统消息

生成医生诊断与处方消息

更新阶段为 pharmacy

5. finish 行为

当前端点击完成就诊时，后端需要：

更新状态为 completed

返回最终 encounter 状态

6. reset 行为

当前端点击重置时，后端需要：

清空当前流程数据

重建初始状态

返回新的初始状态

后端接口清单
POST /encounters

创建新的 encounter

GET /encounters/{encounter_id}

获取当前 encounter 状态

POST /encounters/{encounter_id}/move

更新当前房间

GET /encounters/{encounter_id}/messages

获取消息历史

POST /encounters/{encounter_id}/messages

发送消息并获取 mock 回复

POST /encounters/{encounter_id}/order-test

触发一次 mock 检查

POST /encounters/{encounter_id}/finish

完成就诊

POST /encounters/{encounter_id}/reset

重置流程

后端接口实现要求
1. 返回结构统一

每个接口尽量返回结构化 JSON，便于前端直接消费。

2. 状态推进清晰

不要把流程写散，尽量以 stage 为核心做状态机。

3. 消息可追溯

所有系统消息和角色消息都需要进入 message history。

4. 便于后续替换为 agent

mock 回复逻辑最好封装到 service 层，不要直接写死在 route 层。

后端交付标准

后端完成后，应满足以下标准：

1. 能启动 FastAPI 服务
2. 能创建新的 encounter
3. 能返回初始患者信息和系统消息
4. 能保存并返回消息历史
5. 能根据当前阶段返回固定 mock 对话
6. 能触发固定检查结果
7. 能推进到诊断、处方、药房、完成流程
8. 能支持前端完整联调
